# Methodological decisions

| ID | Decision | Rationale and evidence | Alternative considered | Limitation |
| --- | --- | --- | --- | --- |
| MD-001 | Use hourly common resolution | DAY_AHEAD is hourly; REAL_TIME has twelve five-minute observations/hour. | Keep incompatible native resolutions for comparison. | Loses intra-hour variation in canonical target. |
| MD-002 | System-total load is primary | Three verified regional source columns represent total demand. | Regional-only tasks. | Aggregation can hide regional variation. |
| MD-003 | Aggregate verified wind generators | Phase 2 verifies four wind mappings. | Include all generation. | Plant-level heterogeneity is secondary. |
| MD-004 | Keep utility PV separate from RTPV | Metadata/documentation distinguish Solar PV and Solar RTPV. | Merge all solar. | Excludes a relevant but different solar resource. |
| MD-005 | Preserve DAY_AHEAD as external baseline | Source documentation labels it forecasted and REAL_TIME actual. | Use it as an ordinary ML feature. | May only enter explicit forecast-correction experiments. |
| MD-006 | Use H24 as primary research horizon | Conceptually comparable to RTS DAY_AHEAD. | H1 as primary. | Longer horizon is harder and depends on historical-only covariates. |
| MD-007 | Use H1 as secondary diagnostic horizon | Supports later monitoring and drift scenarios. | Omit short-term analysis. | Not equivalent to DAY_AHEAD. |
| MD-008 | Exclude DAY_AHEAD from independent ML inputs | Prevents embedding an existing forecast. | Forecast correction. | Correction remains a separate future experiment. |
| MD-009 | Fit scaling inside training pipelines only | Prevents validation/test statistics entering transforms. | Global scaling. | Every model pipeline must enforce this. |
| MD-010 | Drop unavailable early-history rows | Missingness represents genuine unavailable lookback. | Global/future imputation. | Reduces sample count. |
| MD-011 | Assign partitions by target timestamp | Resolves horizon-boundary ambiguity. | Index or origin-based splitting. | Historical context can cross partition boundaries. |
| MD-012 | Freeze November–December final test | Preserves unbiased final assessment. | Repeated test feedback. | Two months cannot represent all conditions. |
| MD-013 | Conduct H24-only fixed-configuration feature ablation | Isolates predefined feature-family effects without retuning. | H1 or per-subset tuning. | Full-set hyperparameters may not suit subsets. |
| MD-014 | Rank on F01–F04, confirm on F05–F06 | Prevents confirmation folds from selecting feature sets. | Six-fold ranking. | F05/F06 have prior descriptive exposure. |
| MD-015 | Apply common timestamp intersection and 0.5% simplicity tie-break | Controls sample composition and reduces unnecessary complexity. | Raw subset sample counts or post-hoc tie breaking. | Correlated feature groups remain inseparable. |
| MD-016 | Use MLflow with a repository-local SQLite tracking store and local artifact backend | Supports self-contained, queryable experiment metadata without cloud services. | A bespoke tracker or remote service. | Local validation does not establish distributed scalability. |
| MD-017 | Label pre-Phase-12 records `HISTORICAL_ARTIFACT_IMPORT` and future executions `NATIVE_MLFLOW` | Prevents backfilled evidence from being misrepresented as natively tracked. | Use one undifferentiated origin. | Some historical fields remain `UNKNOWN`. |
| MD-018 | Store repository-relative paths as scientific provenance identity | Preserves device portability while allowing MLflow operational URIs internally. | Canonical absolute paths. | Operational backends still resolve to device-local URIs. |
| MD-019 | Separate research role from development benchmark eligibility | The best internal reference may remain weaker than the strongest comparator. | Infer promotion eligibility from internal rank. | Development gates do not replace final or external validation. |
| MD-020 | Require deterministic model and feature specification fingerprints | Prevents generic labels from collapsing semantically different implementations and features. | Match model names only. | Fingerprints depend on source metadata integrity. |
| MD-021 | Reject invalid evidence from approved registry states | P9-DEV-001 demonstrates that evidence status and implementation identity are governance-critical. | Retain invalid evidence alongside valid candidates. | Audit-only retention remains necessary for transparency. |
| MD-022 | Establish deterministic governance before agentic recommendations | Policy truth must exist before any autonomous component can recommend lifecycle actions. | Build agents and policies together. | Phase 13 evaluates policy behavior without agent interaction. |
| MD-023 | Keep research reference and promotion eligibility independent | Current references are scientifically valid but benchmark-inferior. | Promote the best internal model automatically. | Promotion remains unavailable until every independent gate passes. |
| MD-024 | Gate development benchmark superiority at a frozen 0% margin | A candidate must strictly outperform its predefined strongest development comparator. | Tune a favorable margin. | Development evidence is not final or external validation. |
| MD-025 | Represent lifecycle states and transitions explicitly | Structured transitions make illegal jumps machine-rejectable and auditable. | Use a single ambiguous status. | Real operational systems may require more states later. |
| MD-026 | Require explicit human approval for production-style change | Promotion eligibility cannot authorize activation. | Automatic promotion after metrics pass. | Phase 13 does not integrate organizational IAM. |
| MD-027 | Label simulation approval as `SIMULATION_POLICY` | Synthetic approval can test logic without being misrepresented as human action. | Reuse the human-approved label. | Simulation does not validate real approval operations. |
| MD-028 | Forbid agent bypass of deterministic policy | Later recommendations must remain advisory until all deterministic gates pass. | Allow direct agent state mutation. | Agent behavior is not implemented or evaluated in Phase 13. |
| MD-029 | Bind decisions to policy versions, checksums, and stable fingerprints | Historical decisions must remain interpretable under their original policy. | Reinterpret decisions under the latest policy. | Policy configuration integrity remains a trusted input. |
| MD-030 | Require gate-level deterministic explanations | Every denial must expose evaluated gates, failures, reason codes, and evidence. | Return a Boolean or generated narrative. | Templates explain declared rules, not every organizational nuance. |
| MD-031 | Exclude final-test access from governance simulation | Lifecycle logic can be validated entirely with metadata fixtures and development evidence. | Use final-test performance as a policy input. | Promotion evidence remains development-only. |
| MD-032 | Calibrate drift thresholds on F01-F03 only | Separates monitoring calibration from F04-F06 evaluation and synthetic scenarios. | Tune on monitoring outcomes. | Thresholds may not generalize across years. |
| MD-033 | Use 168-hour windows and 24-hour stride | Captures weekly hourly behavior with daily updates. | Shorter or overlapping arbitrary windows. | Temporal dependence remains. |
| MD-034 | Keep drift observational | Alerts cannot retrain, promote, rollback, or change lifecycle state. | Couple alerts directly to retraining. | Phase 15 will require separate governed requests. |
| MD-035 | Establish deterministic retraining policy before agents | Retraining eligibility must be rule-bound before any autonomous component can propose it. | Build agent-driven retraining first. | Phase 15 evaluates the mechanism without agents. |
| MD-036 | Drift alert ≠ retraining request ≠ promotion | Each transition requires its own evaluated decision; a drift alert is only evidence. | Chain alert→train→deploy. | More governance steps than a naive pipeline. |
| MD-037 | WARNING/CRITICAL-only retraining eligibility with persistence and performance conditions | WATCH/NONE events and feature/prediction-only drift do not authorize retraining. | Retrain on every alert. | Genuine slow drift may need several windows before eligibility. |
| MD-038 | Block retraining on critical data-quality failures | Corrupted data must not produce a challenger (DATA_QUALITY_BLOCK). | Train through corruption. | Recovery then depends on deferred re-request. |
| MD-039 | Enforce label availability and a 336-hour minimum of new labeled data | Retraining may use only labels observable at the cutoff and needs two weeks of post-drift evidence. | Retrain with partial or future labels. | Delays adaptation by design. |
| MD-040 | Apply a 168-hour per-stream retraining cooldown | Prevents repeated retraining every monitoring window. | Retrain at every eligible request. | Rapidly evolving drift may wait one week. |
| MD-041 | Use expanding-window refit as the single retraining strategy | Preserves history, adds post-drift data, and avoids a window hyperparameter search. | Compare multiple window strategies. | One strategy may not be optimal for all drift shapes. |
| MD-042 | Forbid HPO and feature selection during retraining | Challengers must reuse the frozen family, hyperparameters, features, scaling, and seed. | Retune after drift. | Untuned hyperparameters may underperform post-drift optima. |
| MD-043 | Register challengers without promotion eligibility | Successful retraining ends at REGISTERED_CHALLENGER with promotion_eligible=false. | Auto-promote better challengers. | Champion evaluation is deferred to Phase 16. |
| MD-044 | Restrict adaptation experiments to development-only synthetic copies | Controlled target-relationship shifts on copies of the real series with rebuilt features; source data untouched. | Use Phase 14 statistic perturbations or real drift labels. | Synthetic severity design shapes observed gains (concept-drift proxy). |
| MD-045 | Compare challenger against the frozen reference, not external benchmarks, in adaptation scenarios | External RTS DAY_AHEAD values are not coherent forecasts under the modified target process. | Gate adaptation on external benchmarks. | Production-style benchmark eligibility remains unresolved until valid evidence. |
| MD-046 | Establish champion-challenger governance before agents | Promotion decisions must be rule-bound before any autonomous component can request them. | Build agent-driven promotion first. | Phase 16 evaluates the framework without agents. |
| MD-047 | Improved MAE alone never promotes | Superior metrics without registration, lineage, fingerprints, protocol, metadata, evaluation, benchmark, statistical, and approval evidence must be rejected. | Promote the best-MAE challenger. | Valid-looking challengers can be blocked; governance overhead is intentional. |
| MD-048 | Require benchmark evidence for promotion | Synthetic-scenario superiority over a reference is not external development benchmark evidence (Phase 15 MD-045); all 18 real Phase 15 challengers are therefore rejected for promotion. | Accept synthetic-scenario gains as promotion evidence. | No promotion from synthetic evidence; production eligibility remains unresolved. |
| MD-049 | Canary before activation with a zero-regression guardrail | A promoted model must not regress on the canary window; failure rolls back before activation. | Promote directly after approval. | Canary is simulated, not deployed traffic. |
| MD-050 | Preserve and verify before rollback completes | The previous model (artifact, fingerprint, lineage, loadability) must be preserved and restoration verified; failed verification blocks the rollback and is audited. | Best-effort restoration. | A blocked rollback leaves the degraded model active pending operator action. |
| MD-051 | Keep promotion states simulation-scoped | Phase 16 promotion outcomes live in an additive registry; the Phase 13 lifecycle registry is never modified. | Mutate the authoritative lifecycle registry. | No production promotion claim is possible. |
| MD-052 | Defer rather than reject missing approval | A promotion lacking approval is premature, not invalid; rejection is reserved for evidence failures. | Reject unapproved requests. | Approval flow is not integrated with organizational IAM. |
| MD-053 | Build agents as bounded decision support, not controllers | Explanations and reports reduce operational effort while deterministic governance retains authority. | Autonomous agent execution. | Agent value is advisory only. |
| MD-054 | Firewall all agent recommendations with deny-by-default | Only advisory types may pass; lifecycle action types are blocked and audited. | Trust agent output. | Unknown future capabilities are blocked by default. |
| MD-055 | Keep the default backend rule-based and offline | The system must run deterministically without any LLM; LLM text is untrusted advisory input. | Require an LLM API. | Rule-based explanations restate recorded evidence only. |
| MD-056 | Store no chain-of-thought in agent memory | Field-filtered persistence keeps only structured summaries, evidence refs, and outputs. | Persist reasoning traces. | Limits post-hoc analysis of agent internals by design. |
| MD-057 | Require identical lifecycle outcomes in the agentic ablation | The comparison measures operational burden, never model decisions. | Compare decision quality between systems. | Agent value is operational only. |
| MD-058 | Model human workload with a frozen inspection cost model | Deterministic, reproducible baseline without user studies; constants frozen before execution. | Recruit operators. | Approximation, not measured human timing. |
| MD-059 | Keep an explicit verification step in the agentic workflow | The operator verifies the agent-cited evidence, preserving human-in-the-loop reading. | Trust agent references unseen. | Adds a step; the time saving comes from eliminated record scanning. |
| MD-060 | Snapshot protected artifacts around the ablation | Hash-verifies that no policy, threshold, feature, model, or registry changed. | Trust process discipline. | Only listed artifacts are protected. |
